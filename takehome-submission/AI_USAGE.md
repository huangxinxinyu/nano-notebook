# AI_USAGE

## AI 参与的工作

本次开发过程中使用 AI 辅助了以下工作：

- 将题目要求拆成代码、测试知识库、测试问题、输出记录、README、设计说明和 AI 使用记录；
- 检查现有代码是否已经覆盖 Markdown / TXT、Chunk、Hybrid Search、RRF、Rerank、来源引用和多 Source 问答；
- 设计虚构项目 AtlasDesk 的知识库结构；
- 生成确定性的知识库脚本、35 份 Markdown 文档和 10 个测试问题；
- 设计单文档、跨文档、相似信息和知识库不存在答案四类用例；
- 编写本地自动化评测脚本和提交说明；
- 辅助检查测试覆盖、文件数量、文本规模、JSON 格式和相关 Go 测试。

AI 没有替代对代码和结果的检查。关键结论通过阅读仓库实现、运行测试、统计生成文件以及核对测试题预期来源来确认。

## 如何设计和调整检索方案

AI 最初列出了 Keyword Search、BM25、Embedding 和 Hybrid Search 的取舍。结合技术文档既包含精确配置名和数字、又包含自然语言改写这一特点，最终保留现有的 Dense + BM25 + RRF + Rerank 方案。

调整时重点检查了以下问题：

1. Dense 与 BM25 的原始分数不能直接相加，因此使用基于排名的 RRF。
2. Chunk 要服务检索，但不能成为永久引用地址，因此引用定位使用稳定 Evidence Unit。
3. 相似数字必须和对象一起评测，不能只检查答案里是否出现某个数字。
4. 跨文档问题需要验证多个来源是否都被覆盖，而不是只看最终文字是否流畅。
5. 无答案问题需要确认系统不会把关键词相似的段落拼成不存在的结论。

## 对 AI 建议的审查

AI 在讨论 RAG 时容易给出几类过度简化建议，本次没有直接采用：

- “用了 Embedding 就不需要关键词检索”：技术参数、命令和错误码仍适合 BM25。
- “固定按 token 数切分即可”：这会破坏标题、段落和表格边界，也不利于引用定位。
- “把 Top-k 全部塞给模型”：候选过多会增加噪声与成本，需要融合、重排和 Context 上限。
- “低相似度就是无答案”：低分也可能来自改写或索引问题，检索故障也不能等同于知识库无答案。
- “让模型自己输出文件名即可完成引用”：模型生成的字符串不能证明来源真实存在或支持结论，引用必须由服务端校验。

因此，AI 建议只作为备选方案，最终以当前代码约束、数据模型和可验证行为为准。

## 最终方案如何验证

- 运行 Source、Retrieval 和 Agent 相关 Go 测试；
- 验证生成器可重复运行，知识库为 35 个 Markdown 文档、约 3 万字符；
- 使用 JSON 校验器检查 10 个问题的结构；
- 核对问题分布为 5 个单文档、2 个跨文档、1 个相似信息、2 个无答案；
- 对每个有效答案检查文件名和具体章节引用；
- 对相似信息题检查对象与数值是否正确绑定；
- 对无答案题检查是否拒绝猜测以及是否避免无关引用；
- 使用 `run_evaluation.py` 保留可重复执行的本地端到端流程。

## 人工负责的部分

检索架构选择、代码是否符合现有领域模型、测试题是否覆盖题目要求、哪些建议应被拒绝，以及最终提交内容的真实性与完整性，均由候选人负责确认。AI 生成内容在纳入交付物前需要人工复核。
