# 设计说明

## 1. 方案选择

系统使用 Hybrid Search，而不是只做关键词或只做向量检索：

- BM25 擅长命中配置名、错误码、命令和精确数字；
- Dense Retrieval 擅长处理同义表达和自然语言改写；
- RRF 只利用两路排名，不直接比较量纲不同的原始分数；
- Rerank 在融合后的有限候选上进一步排序，控制模型成本。

这一组合适合技术文档：问题可能写成自然语言，但答案通常包含必须精确匹配的参数、文件名或命令。代价是索引链路更复杂，也需要对两路召回和重排分别观测。

## 2. 文档处理与切分

上传文件先被规范化为版本化 Source 内容，再建立稳定的 Evidence Unit。Evidence Unit 尽量对应 Markdown 标题块、段落、表格或其他源文档结构，是引用定位的依据。

检索 Chunk 与引用地址分离。默认 Chunk 参数为：

- 最大 800 个 Unicode 字符；
- 相邻 Chunk 重叠 120 个字符；
- 尽量保留标题上下文；
- Chunk 不跨 Source 或 Evidence Revision。

较小 Chunk 有利于定位精确事实，但上下文容易不足；较大 Chunk 上下文完整，但会降低检索区分度并增加模型输入。当前值适合本次中短篇技术文档，仍应通过离线评测调整，而不是视为通用最优值。

## 3. 检索与 Context 选择

检索流程如下：

```text
问题
  -> 固定 Notebook / Source 范围
  -> Dense 召回 + BM25 召回
  -> RRF 融合
  -> 读取权威 Evidence 内容
  -> Rerank
  -> 有界 Evidence Context
  -> 生成回答与来源引用
```

索引版本记录 Chunk、Embedding、BM25、候选数量、RRF 和 Reranker 参数，使一次检索可以追溯到明确配置。默认开发配置中，Dense 与 BM25 各取 40 个候选，RRF 的 `k` 为 60，再从融合结果中取 20 个候选重排。

Context 不直接拼接整个文档，而是只加入排序靠前、属于本轮固定 Source 集合且能够从权威存储重新解析的 Evidence。这样既减少无关文本，也防止索引中的过期内容绕过 Source 当前版本。

## 4. 来源引用

检索 Chunk 只是可替换的索引表示，不作为长期引用身份。引用通过 Source、Evidence Revision 和 Evidence Unit 解析回原始内容；即使以后重新切分或重建向量索引，已有来源仍能回到权威文档。

展示层至少提供：

- 文件名或 Source 标题；
- 对应段落、Evidence Unit 或可打开的原文位置；
- 多文档答案中的多个来源。

服务端只接受本轮已检索到且仍有访问权限的 Source 引用，过滤无法关联到有效证据的来源标记。

## 5. 降低幻觉与无答案处理

系统通过结构约束而不仅是 Prompt 降低幻觉：

- 每次有已选择 Sources 的问答都必须先执行 `search_evidence`；
- 检索范围固定为用户本轮选择且有权限的 Sources；
- 回答使用有界 Evidence Context；
- 来源由服务端按检索结果校验和发布；
- 检索失败与“文档没有答案”分开处理，避免把系统错误误报为无知识；
- 只有实际使用且可验证的来源才随答案发布。

对知识库不存在的问题，回答应明确说明现有文档没有提供该信息，不猜测具体日期、协议或参数，也不引用仅有关键词相似但不能支持结论的文档。

## 6. 多文档与相似信息

跨文档问题允许从多个 Source 收集 Evidence，再在一个回答中分别陈述各文档贡献。例如认证总览说明支持的登录方式，Refresh Token 文档说明 rotation 与重放撤销，OIDC 文档补充 PKCE 约束。

相似信息不能只按数字合并。测试知识库故意同时放入用户资料缓存 20 分钟、目录缓存 5 分钟、空结果缓存 30 秒和静态资源缓存 86400 秒，并保留旧 Access Token 30 分钟的历史描述。回答必须把数值绑定到对象和文档状态。

## 7. 文档更新与增量索引

Source 内容和 Evidence Revision 分离。文档变更会产生新 Revision，并用当前索引版本重新生成 Chunk 与索引；新索引发布成功前，旧权威版本仍可读取。检索结果携带 Revision 身份，发布引用时再次验证，避免引用被更新或删除后的旧内容。

## 8. 评测方法

本次测试集冻结为 10 题，并为每题记录：

- 分类；
- 预期来源；
- 必须出现的事实；
- 容易混淆时的禁止事实；
- 无答案题的预期行为。

评测时同时检查答案正确性、来源正确性、跨文档覆盖、相似配置区分和无答案行为。后续可加入 Recall@k、MRR、引用精度、答案事实覆盖率、延迟与成本等自动指标。

## 9. 容易失败的情况

- 扫描质量差、表格结构复杂或文本抽取错误时，Evidence 本身可能不完整；
- 专有名词严重拼写错误时，BM25 与 Dense 都可能漏召回；
- 多跳问题需要很多分散证据时，有界 Context 可能漏掉其中一段；
- 多份文档都未标清生效时间时，系统难以可靠判断哪份是现行版本；
- Reranker 不可用时，系统只能按明确降级策略使用融合顺序，排序质量可能下降；
- 文档中存在相互矛盾但没有状态标识时，模型不能替代文档治理来决定真实规则；
- Source 数量和总长度极大时，需要分层检索、Query Rewrite 或 Context Compression 才能维持召回与成本。
